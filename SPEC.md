# «Кузница» (training-journal) — спецификация

> Личный тренировочный сервис с активным анализом. Основной спорт — кроссфит,
> плюс бег / вело. Ввод — Telegram-бот, отчёты — Mini App, источник правды —
> SQLite `training.db`.

Документ решений (что и почему), а не туториал. Проект вырос из plaintext-дневника
в Obsidian (см. §14) в Telegram-сервис; ниже — актуальная архитектура.

---

## 1. Цель

Не архив, а **активный анализ для решений**: управление нагрузкой, подводка к стартам,
прогрессия по уровням, флаги перетренированности, тренерский разбор каждой сессии.
Логирование — средство; ценность — в выводах поверх объективки (часы) + субъективки.

## 2. Два канала данных

Часы — источник правды **не для всего**.
- **Бег / вело / эндьюранс:** часы и есть правда (GPS, темп, мощность, пульс, сплиты).
- **Кроссфит:** часы дают только пульс/калории/strain. Вес, повторы, WOD, scaling,
  счёт/время — это **ручной структурированный ввод**.

Архитектура с самого начала держит оба канала, а не прикручивает кроссфит сбоку.

## 3. Захват кроссфита

Одну каноническую запись кормят несколько источников:

| Способ | Что ловит | Поле |
|---|---|---|
| Фото доски | **предписание** WOD (одинаковое на всю группу) | `prescription` |
| Бот (фото/текст) | **факт**: вес, scaling, счёт/время, RPE | `performed` |
| Часы | биометрия: пульс, зоны, калории, TE | `Activity` |

Фото — **ускоритель, а не истина**: доску стирают, парс может ошибаться. Фото рождает
черновик; истина — подтверждённая запись. Отсюда расщепление схемы на
`prescription`/`performed`: прогрессию считаем like-for-like (Fran RX сегодня быстрее
прошлого?), нагрузку — по **фактическому** весу.

## 4. Архитектура

**Источник правды — SQLite `training.db`** (не plaintext). Три пакета:

```
tj/     ядро: анализ, онтология, нормативы, LLM-клиент, i18n, каноническая схема
tjbot/  Telegram-бот — слой ВВОДА (запись/правка тренировки, программа зала,
        соревнования, цели, самочувствие, профиль, admin, garmin) + training.db
tjapp/  FastAPI Mini App — слой ОТЧЁТОВ (REST + статика; валидация Telegram initData)
```

Бот пишет в `training.db`, Mini App читает из неё через `tj.analysis.*`. «Разбор от
Месье Клода» пишет отдельный скилл `kuznitsa-claude-review` (вне репо).

## 5. Каноническая схема

Vendor-agnostic сущности (`tj/models.py`), таблицы — в `tjbot/db.py`:
- **DailyMetrics** — сон, HRV, пульс покоя, readiness/body battery, стресс, вес.
- **Activity** — сеанс: `source`, `sport`, `start` (с tz!), длительность, ср/макс пульс,
  время в зонах, калории; `extra` (JSON) — богатые поля Garmin + `metcon`/`board`.
- **StrengthWodDetails** — `prescription` (фото) vs `performed` (факт: scaling, load, score, rpe).
- **Competition** (`comp_*`), **discipline_results** (максы → уровни), **goals**.

**Таймзона:** Garmin отдаёт даты в своей логике; «день» вычисляется по локальной tz
пользователя, иначе утренняя тренировка уедет на сутки.

## 6. Ввод тренировки и распознавание

1. Фото доски WOD → **vision** (`tjbot/vision.py`, Gemini) или текст → нотация.
2. **Парсер WOD-нотации** (`tj/analysis/wod_notation.py`/`wod_program.py`) — секции
   (разминка/сила/комплекс), форматы (strength/for_time/amrap/emom/tabata/chipper/
   ladder/benchmark), гомоглиф-толерантность (латиница↔кириллица).
3. **Авто-шаблон результатов** по формату → атлет заполняет → детерминированный разбор
   (`wod_results.py`): силовые максы, метконы (сумма кругов AMRAP, время, счёт).
4. **Онтология** (`tj/ontology.py`) резолвит движения RU/EN → канон. Силовые максы
   (макс-вес, не Эпли) уходят в `discipline_results` → уровни (§7).
5. **Варианты.** Рывок/взятие с маркером (в сед/в стойку, с пола/с виса) резолвятся
   сразу; без маркера — бот **уточняет** инлайн-кнопками, не угадывает.

## 7. Цели и уровни

Каталог дисциплин — `tj/data/standards.json`: **лифты** (нормативы по кратности веса
тела, шкала Strength Level, 5 тиров Новичок→Элита, м/ж) + **бенчмарки** (WOD Girls/Hero,
абсолютные времена/раунды). Уровень считается от **макс-веса** из тренировок
(`best_results`), не от расчётного 1ПМ. Экран целей: заполненные по убыванию, общий
уровень атлета, прогресс до следующего тира. Нормативы — версионируемый JSON, сид при
старте (`seed_standards`).

## 8. Анализ

Поверх `training.db` (`tj/analysis/`):
- **Нагрузка:** ACWR, TRIMP по пульсу, monotony/strain.
- **Готовность:** биометрия Garmin или (без часов) по самооценке `self_feel`.
- **Соревнования:** перцентили, радар способностей (через онтологию), динамика, «в очках».
- **Лидерборд зала**, gym-стата, слияние ручной+garmin записей по (день, спорт).

## 9. LLM-разбор

Два слоя, приоритет **Claude > Gemini > правила/шаблон**:
- **Gemini** (`tj/llm.py`, `tj/analysis/llm_coach.py`) — быстрый разбор по тапу
  «Разобрать ИИ». Текст — бесплатный ключ, vision (фото) — платный. Модель
  `gemini-2.5-flash`, thinking off. Работает только с не-РФ IP (см. §13).
- **Claude** — глубокий «🎩 Разбор от Месье Клода», пишет скилл `kuznitsa-claude-review`
  offline; перекрывает Gemini-разбор за день.
- **Гейтинг:** текстовый разбор Pro-only; суточный лимит вызовов; кэш по хешу payload
  (+ язык, + флаг гадания). Vision-OCR — без Pro (помощник ввода).
- **Астро-хохма:** по желанию (тумблер в Профиле) последним блоком «🔮 Астро-разбор от
  Месье Клода» — юмор по цифрам, не совет.

## 10. Мультиюзер

Данные `training.db` мультиюзерные (ключ `tg_id`, владелец `OWNER_ID`). Приватность —
**режим тренера:** админ видит всех view-only («смотреть как»), обычные юзеры — только
себя. Доступ по allowlist; роли admin/Pro в JSON-файлах (gitignored).

## 11. Garmin

Каждый источник — адаптер (`fetch_daily`/`fetch_activities` + capabilities). Основной —
`garminconnect` (неофициальный, mobile-SSO, DI OAuth токены):
- Авторизация **хрупкая**, периодически падает (Garmin меняет SSO) — раз в неск. месяцев
  обновлять либу. **Токен сохраняем и переиспользуем**, не логинимся каждый запуск.
- **Per-user:** свои часы и часы друзей; пароль не храним (токен-only), MFA — через
  тред-мост в боте (`garmin_connect.py`). Полный дамп — GDPR-экспорт аккаунта.
- Apple Health / Polar / Whoop — задел на потом (у последних есть официальные API).

## 12. Онтология и i18n

- **Онтология** (`tj/ontology.py`): аббревиатуры/синонимы RU/EN → канон (T2B, HSPU,
  «подтягивания до груди», склонения, маркеры вариантов). Растёт со временем; неизвестные
  движения добивает Gemini и учит рантайм-алиасами (`movement_aliases`).
- **Локали RU/EN** (`tj/i18n.py` + `tjapp/static/strings.js`): весь UI и LLM-контент;
  язык = язык реквестера; ворота-тесты на паритет ключей и «нет кириллицы в EN».

## 13. Деплой

Прод — сервер вне РФ (**Gemini API не ходит с росс. IP**). systemd-юниты
`kuznitsa-bot` + `kuznitsa-app`, реверс-прокси **Caddy** (Let's Encrypt) на
твоём домене (например `<your>.duckdns.org`), Mini App на `:8010`. Деплой = `rsync src/` + рестарт сервисов;
данные сервера (`training.db`, `.env`, токены) не перезаписываются; миграции схемы —
идемпотентно в `init_schema`. Бэкап БД — скилл `kuz-ops` (pull-only на мак).

## 14. Legacy: Obsidian/CLI-слой

Проект начинался как plaintext-дневник: истина в md-заметках Obsidian, БД —
пересобираемый кэш, CLI `tj seed/sync/build/analyze/report` (Garmin → `raw/` → канон →
заметки → БД). Слой (`tj/cli.py`, `adapters/`, `vault/`, `store/`) сохранён и рабочий,
но **источник правды переехал в `training.db`**, а основной ввод — бот. CLI полезен для
бэкфилла истории Garmin и офлайн-анализа.
