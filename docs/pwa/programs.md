## Дерево каталога

`program_nodes` (id = slug, `kind` sport | system | program, `status` active | planned | hidden, `sort`, `template_slug`).
`planned` показывается как «скоро» (`soon=True` в `tree()`), `hidden` скрыт. Сид идемпотентен: повторный вызов
обновляет строки по slug из `catalog.json`. Новый вид спорта, система или программа добавляются строкой в JSON
или прямо в таблицу, без кода.

```
Кроссфит (planned)          силовой цикл 5/3/1-стиль, линейная/волна 5×5, бенчмарки,
                            подготовка к Open, конструктор метконов, Hyrox, каталог платных ссылок  (все planned)
ТА (active)
 └─ Болгарская система (active)
     ├─ bulgarian-adaptation   Адаптация: 3 дня, затем рост частоты (12 недель)
     └─ bulgarian-peak-8w      Цикл до теста максимума (8 недель)
Бег (planned)               выносливость, скорость, полумарафон, марафон, скоростные  (все planned)
```

Чужие платные программы (CompTrain, HWPO, PRVN и др.) не копируем, только ссылки в узле «Каталог платных программ».

## Таблицы

- `program_enrollments(id, uid, program_slug, template_version, start_day, status, base_maxes JSON, level, created_at, updated_at, deleted_at)`.
  Одновременно можно быть записанным на разные программы; на одну и ту же дважды при активной записи нельзя (Conflict).
- `program_sessions(id, enrollment_id, planned_day, week, idx, kind, status, plan JSON, checkin JSON, activity_id, updated_at)`.
  `plan` — копия сессии из шаблона на момент записи (обновление шаблона не ломает идущие записи) + `rules`,
  накопленные промахи и развёрнутые подходы.
- `set_log(id, session_id, exercise, planned_kg, done_kg, reps, ok, note, ts, updated_at, deleted_at)`.
  `exercise` — канонический лифт. `id` планового подхода детерминированный (uuid5 от сессии и упражнения), клиент делает `PUT`
  по нему; внеплановые подходы приходят с клиентским UUID и `exercise`.

Все id строки, у строк `updated_at` (ISO UTC, `…Z`), мягкое удаление `deleted_at`.

## Шаблон программы

JSON с версией. Проверка — `validate_template` (`template_errors` даёт список сообщений). Кроме структуры проверяет
смысл: лифты из онтологии и весовые, объявлены в `required_lifts` / `optional_lifts`, дни недели по возрастанию,
нумерация недель и сессий подряд, id упражнений уникальны в сессии, проценты 10..110, `minutes` 10..120.

```json
{
 "schema": 1, "slug": "bulgarian-peak-8w", "version": 1,
 "title": {"ru": "…", "en": "…"}, "summary": {"ru": "…", "en": "…"},
 "params": {"weeks": 8, "session_minutes": [30, 60], "days_per_week": [4, 5]},
 "required_lifts": ["squat_snatch", "clean_and_jerk", "back_squat"],
 "optional_lifts": ["front_squat"],
 "rules": {"on_miss": "drop_5kg_continue", "deload_pct": 70, "illness_drop_pct": 10},
 "weeks": [{
   "week": 4, "type": "medium",                       // volume | medium | high | deload | test
   "title": {"ru": "…", "en": "…"}, "note": {"ru": "…", "en": "…"},
   "sessions": [{
     "idx": 1, "dow": 0, "kind": "normal", "minutes": 40,   // dow: 0 = понедельник
     "title": {"ru": "…", "en": "…"},
     "blocks": [{"title": {"ru": "…", "en": "…"}, "exercises": [
       {"id": "snatch", "lift": "squat_snatch", "name": {"ru": "…", "en": "…"}, "steps": [
         {"ladder": [50, 60, 70, 80, 80], "reps": 1},            // лесенка синглов, повтор процента = ещё сингл
         {"day_max": {"pct": 85, "tries": 2}}                    // «максимум дня»
       ]},
       {"id": "squat", "lift": "back_squat", "name": {"ru": "…", "en": "…"}, "steps": [
         {"pct": 80, "sets": 4, "reps": 3}                       // или {"load": {"lift", "pct", "rounding": 2.5}, "sets", "reps"}
       ]}]}]
   }]
 }]
}
```

Виды шага (ровно один в шаге): `ladder` (элемент — процент или `{pct, reps}`), `sets` (+ `pct` или формула `load`),
`day_max` (`pct`, `tries`), `attempts` (проценты попыток на максимум, каждая тяжелее предыдущей минимум на 2.5 кг).
Вес всегда формула от опорного лифта: `{lift, pct, rounding: 2.5}`, в кг считается при разворачивании.

### Болгарская система: общие принципы, как они легли в шаблоны

Использованы только общие принципы метода, не чужие платные программы.

- Частые короткие тренировки, 30–60 минут.
- Синглы от 50% до опорного процента и «максимум дня» в тяжёлые недели.
- Присед в каждой неделе, тяги не нужны.
- Вес стоит, растёт число синглов, потом +5 пунктов опорного процента (в кг это не «+5 кг», а шаг 5% от максимума).
- Частота тяжёлых дней растёт месяцами. `bulgarian-adaptation`: 12 недель, 3 → 4 → 5 дней по этапам, после каждого этапа
  разгрузочная неделя 70%.
- `bulgarian-peak-8w`: 1 объёмная, 5 средних, 2 высокие недели; последняя сессия недели 8 — `kind=test`: лесенка до 95%,
  затем попытки на 100% (100 / 103 / 106%) по рывку и по взятию и толчку.

Названия и пояснения везде RU + EN.

## Резолвер опорных весов

`program_engine.resolve_reference(con, uid, lift, now, level=None)` → `{lift, kg, source, stale, note, note_en}`.

1. `best`: лучший реальный результат по лифту (`tjbot.db.best_results`, значение веса, не Эпли). Старше 60 дней — `stale=True`;
   если внутри 60 дней есть более свежий (пусть ниже), берётся он.
2. `derived`: от родственного лифта по коэффициентам `DERIVE` (константа с пометкой «оценки, уточняются тест-сессией»):
   squat_snatch ≈ 0.80 × clean_and_jerk, power_snatch ≈ 0.80 × squat_snatch, front_squat ≈ 0.85 × back_squat,
   back_squat ≈ 1.25 × front_squat, clean_floor ≈ 0.90 × clean_and_jerk, jerk ≈ 1.0 × clean_and_jerk и обратные связи.
   Допускается цепочка из двух шагов. `stale` наследуется.
3. `needs_input`: вопрос атлету (`question` RU/EN) и, если в профиле есть пол и вес, `options` из шага 4.
4. `starter`: если передан `level` (`careful` / `normal` / `experienced` = пороги `standards.json` [0] / [1] / [2]):
   порог × вес тела × 0.9, **целые кг**. Пример: мужчина 80 кг, squat_snatch (.47 / .67 / .92) → 34 / 48 / 66.

Округление до 2.5 кг применяется к весам в плане и к производным, стартовые уровни идут целыми (иначе пример из задачи
не сходится: 33.84 → 35, а не 34).

Известное ограничение: `best_results` не смотрит на число повторов, результат 5×100 считается «максимумом 100».
Для лифтов болгарской системы (синглы) это не проблема, для приседа в тест-сессии тоже (попытки — синглы).

## Запись на программу (`enroll`)

`enroll(con, uid, slug, *, start_day, today, base_maxes=None, level=None, weekdays=None, enrollment_id=None)`.

- Узел должен быть `active` и с шаблоном, иначе `Unavailable` («скоро»), нет узла — `NotFound`.
- Снимок `base_maxes` для `required_lifts` + `optional_lifts`: заданные атлетом (`source=user`, служат исходными для
  производных), затем цепочка резолвера. Если для лифта нет ничего и не задан `level`, кидается `NeedsInput` с вопросами по
  каждому такому лифту, в БД ничего не пишется.
- Тест-сессия «день 0»: если у обязательного лифта нет свежего реального макса (нет данных, старше 60 дней, оценка или
  стартовый уровень), в `start_day` создаётся сессия `kind=test`, `week=0` (лесенка 50→95% от оценки и три попытки), а недели
  шаблона начинаются со следующего дня. Заданные атлетом веса тест не вызывают.
- Расписание: неделя 1 привязана к календарной неделе первого дня программы, `planned_day` = понедельник недели + `dow`
  (или свои `weekdays`). Дни до старта сдвигаются вперёд, порядок сохраняется, два занятия в один день не ставятся.
- Идемпотентно по `enrollment_id` (повтор возвращает существующую запись, `existing=True`).

## Сессия

- `plan_session` разворачивает формулы в кг (шаг 2.5, не ниже грифа 20 / 15 кг), пишет плановые строки в `set_log`.
  Повторный вызов пересчитывает только ещё не отмеченные подходы. `get_session` считает то же без записи.
- **Чек-ин** (`submit_checkin`: `energy` 1..5, `tired`, `sleepy`, `joint`, `ill`). Правила детерминированные, причина в `why` / `why_en`:
  устал И (плохо спал ИЛИ energy ≤ 2), либо три сигнала и больше → «неделя 70%» (веса не выше `deload_pct`);
  иначе после болезни → −10 пунктов процента; иначе любой сигнал (устал, болит сустав, плохой сон, energy ≤ 2) → −5 пунктов.
  Тест-сессию не снижаем, только флаг `postpone_advised`.
- **on_miss** `drop_5kg_continue` (`log_set` с `ok=False`): остальные неотмеченные подходы этого лифта в сессии на 5 кг легче,
  другие лифты и уже отмеченные подходы не меняются. Повторный PUT не вычитает второй раз, исправление на `ok=True` снимает поправку,
  второй промах даёт ещё −5. В тест-сессии правило не действует.
- `today_session`: сегодняшняя, иначе начатая, иначе ближайшая, иначе последняя пропущенная. `state`: today | in_progress | upcoming | overdue | none.

## Финиш (`finish_session`)

- Создаёт тренировку `Sport.WEIGHTLIFTING` (source `manual`, `extra.board_source = "program"`, ссылка на запись и сессию) с
  `activity_id` = клиентский UUID (или детерминированный uuid5, если не пришёл), `board_text` = план, результат = подходы, RPE и `feel`.
- Максы (лучший удавшийся подход по лифту, `ok=False` не считается) пишутся через ту же цепочку, что в боте:
  `tjbot.db.record_lift_results` → `discipline_results` с `source='auto'` (дедуп по `activity_id`).
  Лифты без норматива в `standards.json` (jerk, power_clean и др.) в уровни не попадают.
- Тест-сессия: тестированные лифты становятся опорными (`source=test`), оценённые пересчитываются, веса остальных сессий пересчитываются
  при следующем разворачивании.
- Обычная сессия базу **не меняет**. `suggest_base_refresh` предлагает «обновить опорные?», если после старта записи есть макс ≥ базы + 2.5 кг;
  применяет `refresh_base` по явному действию.
- Идемпотентно: повтор по завершённой сессии ничего не пишет (`already=True`). Последняя сессия переводит запись в `done`.
- `day_max_trend(con, uid, lift, window=7)`: максимум дня по лифту за последние `window` тренировок с данными, `trend` up | flat | down | none.

## Онтология: решения

- «толчок» остаётся `clean_and_jerk` (в русской ТА это взятие и толчок), вместе с «толчок в ножницы / в разножку».
- Новый `jerk`: jerk, split jerk, sj, push jerk, power jerk, джерк, толчок со стоек, толчок с груди, толчок от груди, толчок с плеч.
  Алиасы «толчок с груди / от груди», «split jerk», «sj» переехали из `clean_and_jerk`: это именно толчок со стоек.
  `push_press` остаётся швунгом («швунг», «push press»), «швунг-толчок» не заводили.
- Новый `power_clean`: power clean, pc, силовое взятие, пауэр клин, взятие в стойку, взятие на грудь в стойку. Эти алиасы
  ушли из `clean_floor` (он остаётся общим «взятием с пола / на грудь / в сед»), по аналогии с `power_snatch` = «рывок в стойку».
- `snatch_pull` (тяга рывковая, на рывок), `clean_pull` (тяга классическая, на взятие), `hang_snatch` (рывок с виса). Все barbell / weighted.
  «тяга на грудь» остаётся общим `clean`, «становая тяга» — `deadlift`.
- В `standards.json` **не добавлены** jerk и power_clean: тест `test_goals_screen` фиксирует 36 дисциплин, а лишние строки меняют общую
  оценку уровня. Для них есть коэффициенты в `DERIVE`, уровней нет.
- Карта мышц дополнена новыми канонами (тест покрытия онтологии).

## Роуты

Готовы: `src/tjapp/routes/programs.py`, регистрация в `ALL_ROUTERS`, примеры JSON для фронта в `docs/pwa/api-programs-examples.md`.
`seed_catalog` вызывается в lifespan `api.py`. Миграция 0030 лежит в реестре. `finish_session` записывает тренировку и максы
через `tj.services.workouts.save_result`, а не своей логикой. В шаблонах и подходах есть `rest_sec` (таймер отдыха).

Добавлено по итогам фронта: `GET /api/enrollments/{id}/sessions` (календарь: `sets_done` / `sets_total`), поле `refresh` в
`GET /api/enrollments/{id}`, `POST refresh-base` без тела применяет все предложения. `PUT` подхода различает «не передано»
и явный `ok: null` (`model_fields_set` → `fields` в `log_set`): непереданные поля не затираются, `ok: null` без веса — сброс отметки
с пересчётом остатка. Примеры: `docs/pwa/api-programs-examples.md`.
